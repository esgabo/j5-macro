# Running j5 from scripts, CI and agents

j5 runs unattended: everything has a command-line form, nothing waits for a human
unless a terminal is attached, the output can be JSON, and the exit code says how the
run ended. This page is for shell scripts, schedulers, CI jobs and AI agents that start
j5 and read its result.

## The short version

```console
$ j5 run --json --params-file values.yaml --param-env password=FORM_PASSWORD form.yaml \
      > events.jsonl 2> messages.txt < /dev/null
$ echo $?
0
```

- **Exit code**: 0 completed, 1 failed, 2 the script could not be loaded or started
  (invalid script, missing or wrong params), 3 stopped (emergency stop, failsafe,
  interference set to `stop`), 130 interrupted. See [cli.md](cli.md#exit-codes).
- **Output**: with `--json`, standard output carries one JSON event per line; messages
  from `j5` itself go to standard error. See [cli.md](cli.md#json-output).
- **Values**: pass them as params (below), never by editing the script.

## No terminal, no waiting

When standard input is not a terminal (a pipe, `/dev/null`, a scheduler, an agent's
subprocess), `j5 run` never asks anything:

| Situation | With a terminal | Without one |
| --- | --- | --- |
| A required param is missing | Asks for it (secrets without echo) | Exits with code 2 and lists every missing param |
| A `pause:` step or a `break: true` step | Waits for Enter | Resumes on its own and says so on standard error |
| A failed step with `on_error: pause`, or the user moved the mouse | Asks: retry or skip | Retries the step up to twice, then stops the run and exits with code 1 |
| `--step` or `--break` | Interactive debugger | Reads debugger commands from standard input; at its end the run continues to the end |

So an unattended run always ends. For scripts meant to run unattended, prefer
`on_error: retry` (up to 3 attempts) or `on_error: continue` over `pause`.

## Passing values

Params are declared in the script and given on the command line
([scripts.md](scripts.md#params-and-secrets)):

| Source | Option | Good for |
| --- | --- | --- |
| A literal | `--param name=value` | Ordinary values; taken verbatim (`#`, quotes, leading zeros) |
| An environment variable | `--param-env name=VARIABLE` | Secrets from a CI secret store or an agent's environment |
| A file | `--param-file name=path` | Long or multi-line text |
| Standard input | `--param-file name=-` | Piping a value in (then stdin is not a terminal) |
| A YAML or JSON file | `--params-file values.yaml` | Many values at once, generated by another program |

Secret params are masked as `***` in the output and in the run history. Do not pass them
with `--param`: the command line is visible in the process list and shell history. j5
warns when you do.

## Reading the result

Exit code first; for details, the JSON events. Useful event types:

| Event | Tells you |
| --- | --- |
| `run_started` | The `run_id`, seed and backend |
| `step_started` / `step_finished` / `step_failed` | Progress per step, with results and errors (`code`, `message`, `step_id`, `line`) |
| `image_search` | What was searched, the best score and where it was found |
| `log` | The script's `log:` steps and engine messages |
| `run_finished` | `status` (`completed`, `failed`, `stopped`), `reason`, `duration_ms`, `error` |

With `jq`, for example:

```console
$ j5 run --json script.yaml < /dev/null | jq -c 'select(.type == "run_finished") | .payload'
{"status":"completed","duration_ms":3785}
```

Every run is also saved: `j5 runs` lists them and `j5 runs show --json RUN_ID` returns
the events later, with screen captures of failed image searches in the run's folder. See
[cli.md](cli.md#j5-runs).

## Making runs fast and repeatable

- `--fast` replaces the human-like movement and typing with instant input, for when
  nobody needs it to look human.
- `--seed N` makes the human-like randomness repeatable: the same seed, script and screen
  give the same input.
- `--dry-run` checks a script, its params and its image searches without sending input;
  it needs no backend.
- `j5 validate script.yaml` (exit code 1 when invalid) and `j5 validate --json` check a
  script before running it.

## For AI agents

The repository ships an Agent Skill, [skills/j5-macro](../skills/j5-macro/SKILL.md),
that teaches an agent everything below: the authoring loop, script writing, dry runs,
reading events and failure captures, troubleshooting and the safety rules (ask before
sending input, `--allow-exec` only with consent, secrets only through secret params). It
has a script-format cheat sheet, a command reference, validated example scripts and a
small practice window (`skills/j5-macro/scripts/practice_form.py`). To install it, copy
the folder into the agent's skills directory, for Claude Code `~/.claude/skills/` (or a
project's `.claude/skills/`):

```console
$ cp -r skills/j5-macro ~/.claude/skills/
```

The test suite validates its examples and checks that every command and option it shows
exists, so update the skill along with the CLI.

An agent can drive j5 like any shell user:

1. Write or pick a script; `j5 validate --json script.yaml` returns problems with their
   line numbers, which an agent can fix and validate again. `j5 steps --json` lists every
   step type and parameter; `j5 schema` gives the JSON Schema.
2. Run it with `--json`, params from `--params-file` or `--param-env`, and standard input
   closed (`< /dev/null`).
3. Read the exit code and, on failure, the `step_failed` and `run_finished` events: they
   name the step, the line and the error code (`image_not_found` with the best score,
   `window_not_found`, `expression_error`...).

To write the parts of a script that need the screen, an agent uses the authoring tools
without their overlay ([cli.md](cli.md#authoring-tools)); each one sends no input:

```console
$ j5 windows --json                          # titles and client areas
$ j5 screenshot --window Notes               # prints the PNG's path: look at it
$ j5 capture --bbox 812,12,24,24 --window Notes --embed script.yaml --name save_button
$ j5 find '#save_button' --script script.yaml --window Notes --json
$ j5 validate script.yaml
$ j5 run --dry-run script.yaml
$ j5 run script.yaml
```

`--bbox` with `--window` is relative to the window's content, exactly as the window's
screenshot shows it. `j5 find` exits with 1 when the template is not found and reports
the best score, so a capture can be checked before any run.

Things an agent should know:

- **It controls the real mouse and keyboard.** Anything the person at the computer does
  meanwhile can interfere (j5 pauses or stops the run when it notices the mouse moving),
  and j5's input goes to whatever window has the focus. Give scripts a step that focuses
  the right window first.
- **One run at a time.** There is one mouse and one keyboard. Do not start two `j5 run`
  at once against the same display.
- **The emergency stop belongs to the human.** `ctrl+alt+shift+q`, or pushing the mouse
  into a screen corner, stops any run (exit code 3).
- **It needs a desktop session.** On Linux, an X11 session with `DISPLAY` set; on a
  server, a virtual display with `xvfb-run`.

## Driving the engine directly

Programs that need more than one command per run (a GUI, an editor plugin, a long-lived
agent tool) can skip the CLI and speak the engine's protocol: start
`python -m j5_macro.engine` and exchange JSON lines on its standard input and output.
Commands load, validate, run, pause, step, inspect and edit scripts; events report
everything that happens. The protocol is defined in [contract.md](contract.md), and the
engine command's options are in [cli.md](cli.md#the-engine-command). From Python, the
`j5_macro.client.EngineClient` class does the process handling and framing (asyncio). The
VS Code debugger uses the same engine through `j5 dap` ([debugging.md](debugging.md)).
